# AGENTS.md

OpenCode harness: Rust DAG compiled to WASM and loaded in-process by the plugin (no separate runtime service).

## High-value commands

```sh
cargo test                    # fast unit tests for DagEngine
make wasm                     # rebuild plugin/wasm/ from src/lib.rs (requires wasm-pack)
cargo run -- install          # install embedded agents + skills into ~/.config/opencode/
cargo run -- install --force  # overwrite existing installed agent markdown and skills
openagent-harness install     # same install path via built binary
cargo fmt && cargo clippy     # default rustfmt/clippy config
```

- Release CI runs: `make wasm`, `cargo test`, `cargo clippy -- -D warnings`.
- If you change Rust WASM exports or `plugin/harness.ts`'s WASM interface, regenerate `plugin/wasm/` and commit the generated artifacts.

## Entrypoints that matter

- `src/lib.rs`: `DagEngine`, embedded `AGENTS`, wasm exports (`DagEngine` wrapper + `get_agent_configs()`, `append_plan_task()`, `get_plan_draft()`, `discard_plan_draft()`)
- `plugin/harness.ts`: plugin runtime, session/event wiring, ACP calls, event mapping to DAG
- `src/main.rs`: `openagent-harness install [--force]` CLI
- `src/install.rs`: writes embedded agents to `~/.config/opencode/agents/` and skills to `~/.config/opencode/skills/`
- `src/agents.rs`: `parse_agent_frontmatter` — parses `model` from agent `.md` frontmatter; `AgentConfig` — the parsed result
- `src/dag.rs` and `src/types.rs`: `DagEngine.plan_drafts` field stores in-progress `PlanDraft` entries; `PlanDraft` struct holds `id`, `seq` (creation order), `last_touched_seq` (updated on every append, drives true-LRU eviction), and accumulated `tasks`/`agents`
- `src/skills.rs`: `SKILLS` constant with `include_str!` for each embedded skill; `install()` writes to `~/.config/opencode/skills/{name}/SKILL.md`
- `plugin/wasm/`: generated by `make wasm` **and committed** (`.js`, `.d.ts`, `.wasm`)

## Agent capabilities & skills

**Agents (11 total):**
- **orchestrator** (primary) — permissions: question, github_*, harness_cancel, skill (memory/memory-card/memory-context/memory-trace/memory-promote) allow
- **planner** (subagent) — permissions: question, subagent (explorer/researcher/vision), plan_task, save_plan, skill (memory/memory-context) allow
- **explorer** (subagent) — permissions: grep_app_*, skill (caveman/memory-context) allow
- **researcher** (subagent) — permissions: websearch_*, context7_*, grep_app_*, skill (caveman/memory-context) allow
- **vision** (subagent) — permissions: skill (caveman/memory-context) allow
- **builder** (primary+subagent, `mode: all`) — permissions: skill (git-workflow/memory-trace/memory-context) allow
- **builder-junior** (subagent) — permissions: skill (git-worktree) allow (no memory tool access; receives context via auto-injected preamble)
- **reviewer** (primary) — permissions: github_*, grep_app_*, skill (caveman/memory-context) allow
- **consultant** (subagent) — permissions: grep_app_*, skill (memory-context/memory-promote/memory-trace) allow
- **debugger** (subagent) — permissions: skill (memory/memory-card/memory-trace/memory-context/memory-promote) allow
- **docs-writer** (subagent) — model: anthropic/claude-haiku-4-5, permissions: skill (memory-context) allow

**Skills system:**
- Skills are stored at `~/.config/opencode/skills/` — shipped by this repo via `src/skills.rs`.
- `cargo run -- install` installs embedded skills alongside agents.
- Currently shipped: `caveman` (ultra-compressed output mode, ~65% token reduction), `memory` + `memory-card` + `memory-trace` + `memory-context` + `memory-promote`.
- Agents grant skills via `skill` rules in frontmatter `permissions:` (v2 has no per-agent `skills:`/`mcp:` keys; MCP grants are `<server>_*` rules). They must load the skill via the skill tool before acting.
- **caveman** — allowed in frontmatter for: explorer, researcher, vision. (Note: builder, debugger, consultant, reviewer, docs-writer lack a `caveman` skill rule in frontmatter and do not load it, contrary to earlier assumptions.)
- **memory** — router skill; allowed for: orchestrator, planner, debugger. Routes to specific memory sub-skills based on operation.
- **memory-card** — create investigation cards; allowed for: orchestrator, debugger.
- **memory-trace** — log findings to trace.md; allowed for: orchestrator, builder, debugger, consultant.
- **memory-context** — assemble context from cards and system/ knowledge; satisfies acknowledgement gate; allowed for: orchestrator, planner, builder, debugger, consultant, explorer, researcher, reviewer, docs-writer, vision (all agents except builder-junior).
- **memory-promote** — promote findings to system/ knowledge; allowed for: orchestrator, debugger, consultant.
- **git-workflow** — builder: manages worktree lifecycle for parallel junior workers.
- **git-worktree** — builder-junior: enforces atomic seed-commit + autosquash-fixup pattern inside worktree.
- **azure-workflow** — builder, debugger: hard read-only constraint for Azure operations (not shipped by this repo; install separately).
- **pr-workflow** — orchestrator: PR creation and lifecycle management (not shipped by this repo; install separately).

**Builder worktree model:**
- Builder applies `git-workflow` skill before spawning junior workers.
- Creates isolated `git worktree` per junior: path `../work-<task-id>`, branch `ai/*`.
- Each builder-junior spec must include: `worktree_path`, `branch_name`, `base_branch`, `card_number`.
- Builder-junior applies `git-worktree` skill (seed commit + autosquash fixups) inside its worktree.
- Worktrees are cleaned up by builder after juniors complete.

## Runtime behavior (don't mis-assume)

- **OpenCode v2 plugin entrypoint**: `Plugin.define({ id: "openagent-harness", setup(ctx) })` receives `ctx.session`, `ctx.event`, and `ctx.tool` from the host.
- Plugin loads WASM synchronously: `initSync(readFileSync(...))` before hooks run.
- Startup calls `get_agent_configs()` once; missing agent `.md` files are auto-installed on first boot. Stale v1 agent files (with top-level `permission:` key) are auto-overwritten on install.
- Tick loop (`setInterval`, 500ms) only starts tasks (`dag.tick()` + session create/send + `dag.task_started()`).
- Task completion/failure is event-driven: `ctx.event.subscribe()` receives `session.idle`, `session.status`, and `session.execution.failed` events with payload in `event.data` (e.g., `event.data.sessionID`); these are mapped onto v1 names and passed to `dag.process_event()`.
- Session send: `ctx.session.switchAgent()` (if agent) → `ctx.session.switchModel()` (if model) → `ctx.session.prompt({ sessionID, text })` (enqueue only, non-blocking via `/api/session/{id}/prompt`).
- Session errors (`session.execution.failed` events) are mapped to `process_event("session.error", ...)` in the DAG; the engine marks the task `Failed` directly.
- Plugin errors are logged; they are not propagated to OpenCode.
- Tools are registered via `ctx.tool.transform()` with plain JSON Schema; agent gating uses `context.agent` in the execute handler.
- Orchestrator flow: Load the `memory` skill. If the user mentioned a ticket/work item id, call `memory_context({ cardId: "..." })` (create a card first via `memory_card` if it doesn't exist); otherwise call `memory_context({})` (no-card / system-level mode). → Spawn `@planner` with full request (include the card id or "no card" in its prompt). → Planner may clarify via question tool → planner calls `memory_context` (satisfying the gate) → planner builds plan incrementally via `plan_task` (one task per call), threading `plan_id` through all calls and optionally passing `card_id` on each call if a card exists → planner finalizes with `save_plan` (reads accumulated draft via engine, writes `.opencode/plans/{plan_id}.json` with optional `card_id`, discards draft) → orchestrator receives plan → user approval (via question tool) → orchestrator calls `submit_plan` with `native_dispatch: true` → native dispatch loop (`harness_dispatch_tasks` polls for ready tasks; every returned task prompt includes a `<memory-context>` preamble → spawn `subagent` tool calls in parallel with task prompts → `harness_task_complete` per task, which returns `auto_traced: true/false`) → orchestrator calls `memory_promote` for durable findings (with `cardId` if present, else without); if a card exists, calls `memory_trace` with a summary → report results. The orchestrator never submits a workflow without user confirmation.
- **Cancellation:** `harness_cancel({ workflow_id })` or `harness_cancel({ task_id, reason? })` aborts in-flight OpenCode sessions via `ctx.session.interrupt()` (cooperative), removes the sessions, and marks the task(s) `Cancelled`. For `cancel_task`, dependents are also cancelled. Late `session.idle`/`session.execution.failed` events for aborted sessions are dropped. Workflow status becomes `Cancelled` if any Pending/Running task was cancelled; precedence is `Failed` > `Cancelled` > `Done`. The plugin's `harness_dispatch_tasks` treats `"cancelled"` as a terminal workflow status, exiting the native dispatch loop.

## OpenCode v2 plugin API notes

Key implementation details for anyone modifying `plugin/harness.ts` or related code:

- **Model representation**: `ctx.session.switchModel()` takes `{ id, providerID, variant? }`, not a string. The task `model` field is a `provider/model[#variant]` string; conversion happens via `toModelRef()` in `client.ts`, which splits the `#variant` suffix at the first `#` after the provider slash.
- **Tool names are un-namespaced.** All 13 tools (e.g., `submit_workflow`, `plan_task`, `harness_cancel`) are registered with explicit names; no namespace prefix.
- **Events: payload in `event.data`**, not `event.properties`. No `session.error` event type; errors arrive as `session.execution.failed: { sessionID, error: { type, message, status?, response?: {body} } }`.
- **Subagent tool returns**: completed results appear as `<subagent sessionID="ses_..." state="completed">\n<final text>\n</subagent>`. The child session id is also available via `session.created` events with `parentID` and earlier via `context.progress({ sessionID, status: "running" })`.
- **Tool execute context**: `{ sessionID, agent, messageID, id, signal, progress() }`. Agent gating uses `context.agent` to restrict tools (e.g., `orchestrator` only for `submit_workflow`, `submit_plan`).
- **Tool hooks**: `ctx.tool.hook("execute.after", cb)` forwards `{ tool, callID, args, result }`, where `result` is the string result (flattened from content or output). The `execute.before` hook exists in v2 but this plugin does not use it.
- **No toast/TUI API** on server-side plugin ctx. Client-side `showToast()` in `client.ts` is a logged no-op.
- **No `ctx.client` or `ctx.$` in v2.** All session operations go through `ctx.session` methods.
- **Agent frontmatter fields (v2):** `model`, `request`, `system`, `description`, `mode`, `hidden`, `color`, `steps`, `disabled`, `permissions`. Legacy v1 keys (`permission`, `tools`, `prompt`, `disable`, `temperature`, `top_p`, `maxSteps`) are invalid.
- **Permissions: base policy `* * allow`.** Last matching rule wins. `skill` grants use `{ action: "skill", resource: "<id>", effect: "allow" }`. MCP server grants use `{ action: "<server>_*", resource: "*", effect: "allow" }`.

## Non-obvious gotchas

- Model selection: task `model` (if set) is sent to the plugin-created session; otherwise `DEFAULT_MODEL` (`anthropic/claude-sonnet-4-6`) is used. For native-dispatch `subagent` spawns (orchestrator → subagent tool), an agent's frontmatter `model:` applies only if the spawn call does not pass `model`.
- Model string parsing: `provider/model`; if no `/`, provider defaults to `anthropic`; empty string means omit model.
- State persistence is in-memory only; restart loses workflow/task state.
- Rust 2024: `gen` is reserved; do not use it as an identifier.
- The orchestrator agent needs a `question` allow rule in its frontmatter `permissions:` list to use OpenCode's built-in question tool for plan approval. Without this, the question tool calls will be denied.
- The planner agent now also needs the `question` allow rule so it can resolve missing requirements before saving a plan artifact.
- OpenCode v2 agent modes (https://opencode.ai/v2/docs/agents): `mode: primary` agents cannot be launched via the `subagent` tool; use `mode: all` to allow both orchestrator dispatch and subagent spawning. Service restart may be needed after changing an agent's `mode` field.
- Native dispatch: when `submit_plan` is called with `native_dispatch: true`, the orchestrator must run the `harness_dispatch_tasks` / `subagent` tool / `harness_task_complete` loop manually.
- Cancellation: `cancel_task()` returns a JSON object `{"cancelled_task_ids": [...], "session_ids": [...]}` and cascades to all transitive dependents. Cancelled tasks are permanently marked `Cancelled`. Late events for cancelled sessions are silently dropped.
- External skills (git-workflow, azure-workflow, pr-workflow) are NOT shipped by this repo — they must be installed separately. If a declared skill is missing at `~/.config/opencode/skills/`, the agent that needs it will be blocked.
- Builder-junior operates inside a git worktree, not the main repo. Its working directory is `../work-<task-id>` on branch `ai/*`. Never run git operations in the main repo from a junior context. It has no memory tool access; it receives memory findings via the auto-injected prompt preamble.
- Caveman skill is auto-installed by `cargo run -- install` (unlike external skills). It compresses subagent prose output by ~65% via `src/skills.rs` → `~/.config/opencode/skills/caveman/SKILL.md`. Available to explorer, researcher, vision (not orchestrator, builder, builder-junior, debugger, consultant, reviewer, docs-writer).
- Plan drafts are in-memory only (same as workflow/task state); restart loses accumulated drafts. The planner must re-append all tasks if resuming work on a plan.
- Plan-building rule: `plan_id` must be threaded from the first `plan_task` call (which generates a fresh id if omitted) through every subsequent `plan_task` call and to `save_plan`. Reusing a stale `plan_id` (e.g., from a restarted session) seeds a fresh, empty draft — it does not recover tasks from a prior session.
- `depends_on` validation in plan drafts is stricter than `submit_workflow`: indices must reference already-appended tasks only (backward-only, no forward/self-references). Sending `depends_on: [N]` where `N >= current_task_count` is rejected; `submit_workflow` by contrast allows forward references and self-references via looser `dep >= tasks.len()` check.
- `save_plan` on a missing draft or empty draft fails with a distinct error message to prevent accidental persistence of empty plans; a successful `save_plan` reads the draft, writes to disk, then calls `discard_plan_draft` to free memory.
- **Memory acknowledgement gate**: `plan_task`, `submit_plan`, and `submit_workflow` are rejected until the calling session invokes `memory_context` at least once. The gate is **per-session and in-memory only** (lost on restart). Satisfy it with `memory_context({ cardId: "..." })` (with a ticket) or `memory_context({})` (system-level/no-card work). Once called, the gate is cleared for all three operations for that session.
- **v2 `plugins` entries must be directories**; file-path entries are rejected with "configured plugin path must be a directory". v2 resolves a directory plugin via `<dir>/server` or `<dir>/index` (Bun resolve, extension probing), NOT `package.json` `exports`; `plugin/index.ts` re-exports `harness.ts` for this reason. A directory without `index`/`server` is silently skipped (no log). `install.sh` registers `~/.openagent-harness` and migrates old `harness.ts` file entries.
- **Card ID normalization**: empty string `""`, null, or undefined are treated as "no card". A plan draft rejects conflicting `card_id` values on successive `plan_task` calls (e.g., omitting it on the first call, then passing "CARD-123" on the second call, is an error).
- **Submit_workflow WASM signature changed**: The underlying Rust export now accepts an optional `parent_session_id` and `card_id` parameter: `submit_workflow(tasks_json, parent_session_id?, card_id?)`. If you modify `plugin/harness.ts` to directly call the WASM export, regenerate `plugin/wasm/` via `make wasm` and commit the generated artifacts.
- **Auto-injected preamble** on task prompts: every task dispatched via native-dispatch or tick-loop receives a `<memory-context>` block prepended (never modifying the original prompt). Agents should read this block but pass the task prompt through unchanged.
- **Auto-trace on completion/failure**: tasks with `card_id` are auto-traced on completion or failure. Tasks without `card_id` only trace failures and only if exactly one card is active (single-active-card heuristic). Never fatal; filesystem errors during tracing are silently swallowed.
